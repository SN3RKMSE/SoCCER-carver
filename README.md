# Solute Centric Cluster Extraction Routine (SoCCER) v1

Takes a periodic MD LAMMPS trajectory (.lammpstrj) file and converts its dump into carved clusters based on OMol25's carving rule [1]. Outputs are in extended XYZ (extxyz) format.

## Requirements

- Python >= 3.10 (tested with Python 3.12.10)
- NumPy 2.5.4 [2]
- ASE 3.29.0 [3]

## Inputs

Set these in the parameters cell of `SoCCER.ipynb`:

| Parameter | Meaning |
|---|---|
| `trajectory_file` | LAMMPS text dump with an `element` column (read with ASE) |
| `carve_radius` | R, in Å |
| `solute_atoms` | `[index, symbol]` for each solute atom, 0-based, in dump order |
| `solvent_atoms` | element order of one solvent molecule |
| `output_directory` | folder for the output files |

Please refer to the sample notebook for a clearer picture.

## Output

- One file per frame: `cluster_<timestep>.xyz` (extxyz), `pbc="F F F"`, no cell.
- Header: `timestep`, `n_solvent`, `centre_shift`.
- Per-atom column: `atom_id`, the 1-based id of each atom in the original frame.
- Row order: solute atoms in `solute_atoms` order, then solvent molecules in increasing molecule index.
- Back to MD coordinates: position + `centre_shift` gives the coordinates in the unwrapped frame of the first solute
  atom.

## Usage

Edit the parameters cell and run all cells. Please refer to the example shown in this repository. **The output directory mentioned in the input cell must exist in the directory for the code to work.**

Demonstration/ contains 5 frames from a classical MD run of Li₂S₈ in DME (20,010 atoms, both Li restrained near the chain). With R = 5 Å, your output should match Demonstration/expected_outputs/.

## Assumptions

Kindly note that the following assumptions were made in making this code.
 - The simulation box from the MD run is **orthorhombic**.
 - The box is periodic in all 3 directions. If in a certain use case PBC is not present, simply change the box size to be much larger and set PBC as shown: 
   ```python
   frame.set_cell(frame.cell.lengths() * 5, scale_atoms=False)
   frame.pbc = True
   ```
   (Place these lines inside the frame loop, before carver(frame, ...).)
   This ensures that no component of any distance vector is ever larger than L/2, and thus MIC is never triggered.
 - **Contiguous blocks:** When using Packmol to generate the starting configurations, it was seen that the molecules have all their atoms written continuously and in a fixed order, with the solute atoms forming one block sitting between whole solvent molecules. If atomic ordering is broken, this script will not work properly and generate broken outputs, please check the inputs. 
 - **Very Large Box Compared to the Components:** The solute and each solvent molecule span less than half the box length in every direction, so the minimum image gives the bonded image.
 - There is only **one type of solvent molecule**. Multiple solvents are currently not supported.
 - The solute may contain several molecules or ions only if they form one contiguous block and stay close together (see Contiguous blocks and Very Large Box).

## Method (Briefly)

 - Minimum-image vectors are taken from every solute atom to every solvent atom. (NumPy broadcasting is used for vectorised calculations to increase speed.)
 - A solvent molecule is included if any of its atoms is **strictly closer than R** to any solute atom; the closest (solute atom, solvent atom) pair is recorded.
 - The solute is made whole around its first atom. (By the Large Box assumption, the largest distance between any two atoms of the solute is still less than the distance L/2. This was true in our classical explorer MD simulations.)
 - Each included molecule is made whole around its contact atom, then translated so the contact atom sits at the unwrapped solute atom plus the minimum-image vector.
 - The cluster is centred on the mean of all its atom positions. The clusters include which timestep they were carved from and the number of solvent molecules in the carve, done for better traceability and easier statistics on cluster atom counts.
 - One extxyz file is written per frame.

## Speed 

This code has undergone a few iterations in terms of design. The first few designs were based on a neighbour list construction (from ASE's inbuilt libraries), and comparing distances from there. However, this was very slow on benchmarking (100 snapshots of 20,010 atoms, with carve radius 5 Å took 228.0 s for the scripts to run end to end on an Intel Core 5 210H laptop.) 
The current version uses NumPy broadcasting for vectorised distance calculations over the solute-solvent distances only. It took 3.9 s to run end to end and matches all outputs generated by the previous prototype. 
Parallelisation: The dump file can be split into multiple smaller dump files and run on parallel CPUs. No calculation for one frame depends on the other, so SoCCER is highly parallelisable.
Any suggestions on improving the speed further are happily welcome.

## Future Plans

Most of the plans involve higher generality, which include:

- **Bond-graph unwrapping:** make molecules whole by following bonds, so large or extended solutes no longer need to span less than half the box.
- **Non-orthorhombic boxes:** support triclinic cells in the distance calculation.
- **Multiple solvent species:** handle mixed solvents directly, without any changes to the input file.
- **Charge and multiplicity:** assign these to each cluster from user-defined values, so the output is ready for DFT.
- **Counter-ion handling:** an optional rule for dropping solute ions that are far from the rest of the solute.
- **Input checks:** optional bond and topology checks, to catch input that breaks the assumptions above.
- **Built-in parallel runs:** split a dump and carve the pieces in parallel automatically.

All these will be made and released with the manuscript. Any other suggestions on improving the code are happily welcome.
